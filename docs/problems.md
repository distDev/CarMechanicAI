# Problems Module

## Назначение

Problems — центральный модуль системы CarAI.

Он отвечает за управление жизненным циклом проблемы автомобиля и является точкой входа для всех последующих процессов:

- AI диагностика;
- ремонт;
- история обслуживания.

Модуль **не занимается диагностикой или ремонтом**. Его задача — хранить информацию о проблеме и управлять ее состоянием.

---

# Ответственность модуля

Problems отвечает только за следующие задачи:

- создание новой проблемы;
- хранение пользовательского описания;
- хранение кода ошибки (если указан);
- хранение фотографий проблемы;
- создание первой сессии диагностики;
- управление статусом проблемы;
- предоставление списка проблем автомобиля.

Модуль **не отвечает** за:

- AI анализ;
- подтверждение причины;
- ремонт;
- чат;
- генерацию инструкций.

Все эти задачи реализуются отдельными модулями.

---

# Жизненный цикл Problem

После создания проблема автоматически переходит в диагностику.

```text
DIAGNOSING
      │
      ├──────────────► CLOSED
      │
      ▼
REPAIRING
      │
      ▼
RESOLVED
      │
      ▼
CLOSED
```

Статус NEW в системе не используется.

После создания проблема сразу получает статус:

```text
DIAGNOSING
```

---

# Допустимые переходы

Разрешены только следующие переходы:

| Текущий статус | Новый статус |
| -------------- | ------------ |
| DIAGNOSING     | REPAIRING    |
| DIAGNOSING     | CLOSED       |
| REPAIRING      | RESOLVED     |
| RESOLVED       | CLOSED       |

Любой другой переход считается ошибкой бизнес-логики.

Проверка переходов выполняется внутри `ProblemService`.

---

# Работа с фотографиями

При создании проблемы пользователь может прикрепить фотографии.

Фотографии используются исключительно для AI диагностики.

После создания проблемы фотографии являются неизменяемыми.

Удаление, добавление и редактирование фотографий не поддерживается.

---

## Где хранятся фотографии

Файлы сохраняются через `FileUploadService`.

Problems не знает, какое используется файловое хранилище.

Это может быть:

- Local Storage;
- MinIO;
- Amazon S3;
- любой другой StorageProvider.

Problems взаимодействует только с `FileUploadService`.

---

## Что хранится в базе данных

В таблице `problem_photos` хранится только путь к файлу.

Пример:

```text
problems/ef98f3f0-....png
```

Полный URL не хранится.

Он формируется `FileUploadService` в зависимости от выбранного хранилища.

Такой подход позволяет менять файловое хранилище без изменения структуры базы данных.

---

# Создание проблемы

При создании выполняются следующие действия:

1. Проверяется принадлежность автомобиля пользователю.
2. Загружаются фотографии.
3. Создается запись Problem.
4. Создаются записи ProblemPhoto.
5. Создается первая DiagnosisSession.
6. Возвращается краткая информация о созданной проблеме.

Если на любом этапе возникает ошибка после загрузки файлов, выполняется компенсация:

- все загруженные файлы удаляются из хранилища;
- исключение пробрасывается выше.

Это гарантирует отсутствие "мусорных" файлов.

---

# Работа с другими модулями

Problems является владельцем состояния проблемы.

Другие модули **не должны** напрямую изменять таблицу `problems`.

Например, запрещено:

```ts
await prisma.problem.update(...)
```

Все изменения состояния должны происходить только через `ProblemService`.

---

## Изменение статуса

Для изменения статуса используется публичный метод:

```ts
problemService.updateStatus(problemId, status);
```

Он:

1. загружает Problem;
2. проверяет допустимость перехода;
3. изменяет статус;
4. возвращает обновленную информацию.

---

## Пример использования

После завершения диагностики:

```ts
await problemService.updateStatus(problemId, ProblemStatus.REPAIRING);
```

После завершения ремонта:

```ts
await problemService.updateStatus(problemId, ProblemStatus.RESOLVED);
```

При закрытии пользователем:

```ts
await problemService.updateStatus(problemId, ProblemStatus.CLOSED);
```

Таким образом все бизнес-правила изменения статуса сосредоточены в одном месте.

---

# Взаимодействие с Diagnosis

После создания Problem автоматически создается первая `DiagnosisSession`.

Problems не выполняет диагностику.

Он только инициирует первую диагностическую сессию.

В дальнейшем модуль Diagnosis полностью управляет процессом диагностики.

---

# Взаимодействие с Repair

После подтверждения причины модуль Diagnosis переводит Problem в состояние:

```text
REPAIRING
```

После завершения ремонта модуль Repair переводит Problem в:

```text
RESOLVED
```

Problems не знает деталей ремонта.

Он хранит только итоговый статус.

---

# API

## Создание проблемы

```http
POST /problems
```

Создает новую проблему, загружает фотографии и создает первую диагностическую сессию.

---

## Получение списка проблем автомобиля

```http
GET /vehicles/:vehicleId/problems
```

Возвращает краткую информацию обо всех проблемах автомобиля.

---

## Получение полной информации

```http
GET /problems/:id
```

Зарезервировано.

Будет реализовано после завершения модулей Diagnosis и Repair.

---

## Изменение статуса

```http
PATCH /problems/:id/status
```

Используется пользователем для закрытия проблемы.

Внутренние модули (`Diagnosis`, `Repair`) изменяют статус через `ProblemService`, а не через HTTP API.

---

# Основные принципы

- Problems — центральная бизнес-сущность системы.
- Problems не содержит бизнес-логику диагностики и ремонта.
- Problems владеет жизненным циклом проблемы.
- Только `ProblemService` может изменять статус.
- Фотографии после создания являются неизменяемыми.
- URL файлов не хранится в базе данных.
- Любые ошибки после загрузки файлов приводят к их автоматическому удалению.
